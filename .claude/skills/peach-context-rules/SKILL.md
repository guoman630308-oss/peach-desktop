# 上下文写作与清退

最后复核：2026-10-18
证据来源：ADR-0015、`scripts/check_context_budget.py`、`tests/test_context_budget.py`、用户于
2026-08-17 提供的 `My AGENTS.md & SKILLS.md Breakdown` 逐字稿。

判据与理由的完整版在 `docs/adr/0015-agent-context-layering.md`，本文件只给操作步骤。

## 新增一条规则

按顺序回答，第一个命中的就是归属：

1. 不遵守会直接损坏真实数据、破坏生产或产出假结论，且任何任务都可能触发？
   → `AGENTS.md`，一行祈使句 + 指向可执行入口。
2. 只有某类任务才需要，且是「步骤」？→ 新建或补充 `.claude/skills/<name>/SKILL.md`。
3. 是通用契约、复用依据或架构取舍？→ 对应产品文档、`docs/REUSE.md` 或 ADR。
   本机运行事实、馆藏盘点、个人待办与交接只存 `<数据根>/state/project-context/` 等仓库外目录。
4. 与仓库无关、跨项目成立？→ 当前智能体全局入口（Codex 为 `~/.codex/AGENTS.md`，
   Claude 为 `~/.claude/CLAUDE.md`）；成套流程进入对应用户级技能，事实进入按需参考文档。
5. 只对本次对话有效？→ 不写入任何文件。

补充要求：

- 规则必须来自本项目的真实失败或真实决策。禁止照搬外部模板或别人的 `AGENTS.md`：
  别人的条文对应的是别人的失败模式，抄来的规则没有可指认的来源，第一次复核就该删。
- 能配一对**坏例 / 好例**就配上，比抽象形容词有效得多。仓库里已有的范例：`bba0b77` 的
  测试与实现拆分提交、`duration=0` 与失败值 `-1`、`ABW` 与 `ABW 番号` 的搜索推荐词。
- 同一事实只能有一处真相。技能引用文档路径，不复制数字。
- 一条规则如果能变成脚本拒绝、测试失败或 hook 行为，就先把门槛做出来，散文只留一行指路。
- `AGENTS.md` 不是 `README.md`：README 讲这个项目是什么、怎么跑；`AGENTS.md` 讲改动它之前
  必须知道什么。同一段内容不要两边都写。

## 写 description

description 会常驻上下文，**技能没被触发时也在消耗预算**。所以它的任务是「让模型知道什么时候
把这份技能拉进来」，不是解释技能内容。

- 简短说明具体任务与适用边界；关键词须对应真实使用场景，不因相邻主题触发。
- description 不塞步骤，多流程技能用最小路由指向按需参考。
- 坏例：`Peach 并行代码任务的 Git worktree 隔离、暂存边界、测试入口与集成流程。`
- 好例：`创建、提交、集成或回收 Peach 工作树时使用。`
- 一个技能同时管两件常被单独需要的事（例如「写 PR」和「盯 PR」）就拆成两个，各写各的触发词。

## 新建技能

```text
.claude/skills/<name>/SKILL.md
```

- frontmatter 只有 `name`（与目录同名）和 `description`（≤ 200 字符）。
- 正文前两行固定为 `最后复核：YYYY-MM-DD` 和 `证据来源：`。
- 正文预算以 `scripts/check_context_budget.py` 为准。超出时按职责下沉通用事实，私有信息移出仓库。
- 在 `AGENTS.md` 的技能索引表加一行触发条件与路径，Codex 靠这张表按需读取。

行数、字节数、单行长度与 description 的预算由同一检查器维护，本技能不复写数值。

## 预算只能降不能升

调低随时可以。上调必须在 `scripts/check_context_budget.py` 的 `BUDGET_CHANGES` 追加
「值 / 日期 / 理由」，理由要说明这些内容为什么无法下沉到 `docs/` 或技能；写「初始值」或留空
判错。`MAX_EVER` 是天花板，不因为写超了而调整。

## 触发是概率性的，别拿技能当门槛

Claude 只把每个技能的 name+description 预加载进系统提示，读不读正文由模型按 description 判断；
Codex 完全不自动加载 `.claude/skills`，只能靠 `AGENTS.md` 索引表主动读。所以「必须每次成立」的
规则不能只写成技能，必须同时有脚本、测试或 hook 强制。技能写「怎么做」，门槛写「必须做」。

## 文案只写最终状态

界面字串、注释、docstring、测试名与文档只描述现在成立的行为和约束，不叙述被否掉的做法，
也不做改动前后对比，因为版本演进由 Git 记录，读者要的是当前这一份怎么用。

- 门槛是 `scripts/check_copy_final_state.py`，由 `tests/test_copy_final_state.py` 在 tooling
  与 web 两个域执行；词表、覆盖面与临时例外文件清单都在脚本顶部，改判据就改那里。
- 覆盖面：`web/` 的字串与注释、`frontend/`，`src`/`scripts`/`tests` 的注释、docstring、
  字符串字面量与测试函数名，以及 `README.md`、`docs/*.md`（不含 `docs/adr/`）、`AGENTS.md`
  和各技能正文。ADR 正文按定义要记录决策过程，不在覆盖面内。
- 约束的理由必须留下。把它写成反事实句「这样做的话，会……」，说清失败模式而不点名某一版实现，
  既保住教训又不需要放行标记。
- 真实事故记录才放行：那一行结尾加 `copy-lint-disable-line`，Markdown 写成 HTML 注释、
  Python 用 `#`、JS 用 `//`；这个标记与用户级 `lint_copy_rules.py` 共用，一处标记两边都认。
  放行前先试着改写成「现在的规则 + 它防住的后果」，多数记录不需要标记。

## 失败模式审计

规则的来源应该是统计，不是印象。定期（每次 minor 发布前，或连续踩同类坑时）让智能体审计
本机的会话历史与 Git 历史，按模型和 harness 分类统计高频失败：误杀进程、跑错测试入口、
只改一个影响面、把候选当真相、把提醒当门槛。产出一份可核对的清单，再决定：

- 高频且可自动检测 → 做成门槛（脚本 / 测试 / hook）。
- 高频但只能靠判断 → 写进 `AGENTS.md` 硬门槛或对应技能，并配坏例/好例。
- 低频且已被门槛覆盖 → 直接清退。

任务耗时或产出明显偏离预期时，核对工具记录与实际失败，判断是否有无关读取、重复验证或授权歧义。
精简后用文档小改、行为修复、真实数据操作等代表性场景复核触发、完成标准和授权边界；
静态检查只证明结构与门槛成立，不证明模型效率改善。

## 清退

触发时机：相关实现被删除或重写、规则已被可执行门槛覆盖、预算检查失败、每次 minor 版本发布、
失败模式审计给出新结论。

步骤：

1. 运行 `python scripts/check_context_budget.py`：退出码 0 通过，1 有超预算或结构错误，3 只有 `最后复核` 超过 180 天的条目。

2. 逐条问：这条规则的事故或证据还能指认吗？对应实现还在吗？已经有门槛了吗？
3. 该删就整段删除，不留「已废弃」注释，Git 就是归档。被 ADR 取代的段落只留一行指向 ADR。
4. 复核但保留的技能更新 `最后复核` 日期。
5. 结构与预算由 `tests/test_context_budget.py` 在 `& .\scripts\test.ps1` 中强制执行。

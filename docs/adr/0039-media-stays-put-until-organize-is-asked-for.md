# ADR-0039：媒体默认留在原处，整理是显式、可预览、可回滚的操作

- 状态：Accepted
- 日期：2026-09-22

## 背景

README 的「数据边界」一直承诺媒体保留在原目录：Peach 只读盘、只写账本，用户在资源管理器里
看到的目录结构不会因为装了 Peach 而变样。这条承诺换来的信任是真的：用户敢把十几年攒的
目录交给它扫。

但用户同时想要整理：文件名里带着盗版站的域名，目录层级是各个来源随手堆出来的，同一个厂牌
散在三处。`scripts/clean_names.py` 与 `scripts/flatten_release_dirs.py` 已经能出 dry-run 计划，
落地那一步却只存在于待办里，而且它们各自只处理一种形态（域名噪声、冗余目录层），没有「按我
说的样子命名」这件事。

参考实现 amane 把路径模板挂在库上（`video_template` 等），占位符从数据库真相字段取值，
`[...]` 可选分组在占位符为空时整段省略，整理是独立任务、库级锁串行、只手动触发。它的另一半
前提不能借：那边文件是数据库的派生副产物，可以生成 STRM、软链，也可以删。Peach 这边文件是
真相的载体，账本才是派生的。

## 决策

**一、默认一个字节都不动。** 扫描、刮削、抽帧、对账都不改路径。整理只在用户点下去的那一次
发生，没有自动触发、没有调度器、没有「顺带整理」。

**二、模板挂在来源根上。** 用户对每个来源（`local` / `115` / `pikpak`）配置一份文件名模板和
一份目录模板，存在 `profile.settings_json` 的 `organizeTemplates` 里，跟着账本走。占位符
`{number}` `{title}` `{studio}` `{year}` `{actors}` `{series}` `{cd}` `{mosaic}` `{definition}`
只从 approved 真相字段取值，候选一律不参与，因为按未复核的猜测改文件名，等于把猜测写进了
文件系统，而那一层没有 `source` 和 `confidence` 可言。`[...]` 分组里的占位符为空时整段省略。

**三、预览与执行分两步，中间隔着一份 CSV。** 预览逐文件生成计划写进 `GENERATED_DIR`，
每行带资产 id、当前路径、目标路径、动作与跳过原因；执行只接受用户确认过的同一组模板。
结论落在文件里而不是只存在于界面，重放和事后追查才有依据。

**四、只在同一个卷里动。** 目标一律是「同目录改名」或「移进同一个来源根下的模板子目录」。
跨盘整行拒绝，不做复制加删除：跨盘移动是读一遍写一遍，中断就是半个文件，而 115 与 PikPak
的「盘」是网络挂载，一次移动就是把几个 G 拖下来再传上去。

**五、目标已存在就整行失败，不覆盖、不加序号。** 撞名说明两条记录指向同一个名字，那是要人
看的信号，不是自动消歧的机会。`clean_names.py` 的 ` (3)` 序号同理保留，用于区分同秒落地的文件。

**六、每个执行批次先 SQLite backup，再写一份 `(old_path,new_path)` 批次日志。** 界面提供
「回滚上一批」：按日志逆序把文件改回去并同步账本。失败的行单独报，不影响其余行。

**七、整理期间与其他整理互斥。** 走既有的 `BackgroundJob` + `task_run`，任务键 `organize`，
在任务中心留一条记录。手动触发撞上在跑的那一轮时返回 409，而不是并发两批改同一棵目录树。

**八、路径存在性只用挂载判定，不做目录遍历。** 来源不在线时整批跳过。预览不对每一行发一次
`stat`：115 与 PikPak 的挂载上那是一次网络往返，几万行就是几万次。撞名由执行那一步在
`rename` 前当场判，判不过的那一行失败，别的行照常。

README 的「数据边界」因此改成「媒体默认保留在原目录，整理是用户显式发起、可预览可回滚的
操作」。

## 被否决的方案

- **让扫描顺带规范命名。** 那就变成「装了 Peach 它自己改了我的文件」，README 那句承诺也就
  没法写了。整理必须是用户的动作。
- **像 amane 那样把文件当数据库的派生物，允许生成软链与删除。** Peach 的真相源是账本，但
  账本记的是「盘上这个文件」；文件没了，账本那一行就指不到任何东西。软链在 115 挂载和
  Windows 上都不成立。
- **跨盘移动。** 见决策四。用户想换盘时用资源管理器，那是他要盯着的事。
- **撞名时自动补 `(2)`。** 整理的目的是让名字可预期；自动消歧会让两部不同的片以序号区分，
  而序号说明不了它们哪里不同。
- **把模板写进设置文件（`config.toml`）。** 那份文件是本机运行坐标，模板是用户习惯，跟着
  账本走才能两台机器一致。

## 后果

- 待办第 9 项从「只有 dry-run」推进到「界面上能预览、能执行、能回滚」，`clean_names.py` 与
  `flatten_release_dirs.py` 仍各自负责它们那两种专门形态。
- 多一类 `organize` 任务记录，多一份批次日志目录 `GENERATED_DIR/organize-batches/`。
- 只读端（reader）不放行执行与回滚：它那份账本是复制来的，改了就是一处合不回去的分叉。
- 用户第一次真正能让 Peach 动他的文件，所以这一步的每一个环节都要能答出「动了哪些、怎么
  退回去」。

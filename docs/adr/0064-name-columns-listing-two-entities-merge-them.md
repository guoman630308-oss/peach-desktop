# ADR-0064：名字栏把两条女优实体列成同一个人时自动合并

- 状态：Accepted
- 日期：2026-09-24
- 修订：ADR-0055 第六条（被占用的写法只记进复核产物）与「后果」第一条；ADR-0063「后果」第一条
- 依据：ADR-0052（实体层证据充分即落库）、`peach-ledger-write`「实体合并」

## 背景

实体 9128「雪代一鳳」与 9129「雪代美鳳」各挂 4 部作品，javdb 上是两个演员页。av_neme 的
`雪代一鳳` 是一张改名页，跟到 `雪代美鳳` 人物页，名字栏同时列着这两个名字。按 ADR-0055 第六条，
补别名后继只把「雪代一鳳 已被实体 9128 用着」记进 `performer-alias-landing.csv`，两条实体照旧
各占一页、各有一份头像与作品数。同一位女优换过艺名而两个名字都登记成实体，是补别名后继
每轮都会撞到的情形；复核产物里的这些行没有界面入口，等人翻文件再手工合并，等于不合并。

用户 2026-09-24 决定：这种情形自动合。

## 决策

**一、合并判据。** 补别名后继按 ADR-0055 双向核对进到她的人物页之后，页上被占用的写法
（`TAKEN`）如果全部指向同一条另外的女优实体，且只来自 minnano-av 或 av_neme 的名字栏
（`MERGE_SITES`），就把两条合成一条。被占用的写法指向两条以上实体，或某个写法有两个以上
占用者，页上的人比账本里多，不合，照旧记「占用」。fc2cmadb 的曾用名栏混着卖家起的商品名
（ADR-0061 第四条），它给的「占用」不作合并证据。

**二、保留哪一侧。** 作品多的一侧留下；一样多时，页上主名（名字栏第一格）是谁的名字就留谁；
再一样留先登记的（本条后继正在处理的那条）。被并入的规范名与全部别名、作品关系、外部引用、
链接、检索词与归属都按 `peach.entities.merge_entity` 迁过去；这一轮先落在被并入那一侧的新写法
也跟着过去。

**三、备份与校验。** 合并前用 `sqlite_backup` 把账本备到数据库目录，文件名
`ledger.pre-alias-merge-<时间>-<被并入实体 id>.db`，托盘启动时按 `ledger_backups` 的保留规则
清退。合并在一个写事务里做完，随即 `PRAGMA foreign_key_check`，不为 0 就抛错、事务回滚，
这条后继判失败。

**四、留痕。** 被并入的名字以 `merge:auto:performer-alias@<任务行 id>` 为来源写进
`entity_alias`；复核产物里那几行「占用」改成「合并」，判词写明谁并入谁、迁了几部作品；后继摘要
带 `merged`（保留与被并入的实体 id、名字、作品数、备份文件名），活动页那一行的结论写
「X 并入 Y」。`scripts/revert_auto_landing.py` 撤不回合并，要退回只能从那份备份恢复。

## 后果

- 合并是不可逆的账本写入，此前一律要当场授权；本 ADR 把「两站名字栏把两条实体列成同一个人」
  这一种判据确定的情形交给后继直接做，其余合并仍按 `peach-ledger-write` 授权。
- 保留一侧的名字链因为多了 `merge:*` 来源的别名而指纹改变，下一轮存量补派会再问一次两站，
  用新写法把剩下的页补齐。
- 一张页列着三条以上实体时不合。那说明账本里这个人被拆成了三份，或者页上把两个人写在了一起，
  两种都得人看。

# ADR-0041：新文件由事件推进来，全量扫描只负责补漏

- 状态：Accepted
- 日期：2026-09-22

## 背景

Peach 认识一个新文件的唯一途径是全量扫描：遍历三个来源根，逐个 `stat`，比对账本。用户存完
一部片，要等下一轮扫描跑到才能在界面上看见。

三个来源的代价还差得很远。`R:` 是真本地外置盘，遍历便宜。`B:`（115）和 `A:`（PikPak）是
CloudDrive 挂载，虽然在资源管理器里长得和本地盘一样，但每一次列目录都是网络请求：本机上
误判过一次，一轮遍历读掉了 167 GB。所以全量扫描的频率被这两个盘钉死在「不能勤」，而用户
真正在意的恰恰是刚存进网盘的那一部。

参考实现 `sqzw-x/amane` 的 Watcher 把这件事拆成两条通道：本地目录订阅文件系统事件，网盘
目录等 CloudDrive2 主动推 webhook 过来。取证见 [docs/reference-snapshots/amane-watcher.md](../reference-snapshots/amane-watcher.md)。

## 决策

**一、事件只是一个触发器，入库逻辑只有一份。** 事件带来的是一条路径，拿到之后走的是
`scan.ingest_path`，和 `scan_location` 共用 `check_scan_target`、`walk_root_for`、媒介判定、
同一条 upsert 语句和同一套字幕配对。不新建第二条「快速入库」路径：两条登记逻辑迟早会对
同一个文件给出两种账本行，而它们的分歧没人会去看。

**二、本地通道只监视 `local` 来源的根。** `watchdog` 订阅 `R:` 这样的真本地盘。`A:` 与 `B:`
一概不监视：给网络挂载挂递归 watcher，等于持续轮询网盘。它们的新文件走第二条通道。

**三、网盘通道是 CloudDrive2 推过来的一个 HTTP 请求。** 端点 `POST /api/inbox/clouddrive`，
请求体是 CloudDrive2 的 `[file_system_watcher]` 格式；只取 `create` 与 `rename`，`rename`
取目标路径，目录事件丢掉。删除事件不处理：脱盘与消失由既有的对账那一路判，一条推送不足以
断定一个文件真的没了。

**四、云端路径不进 `pathlib`，只查前缀表。** CloudDrive2 报的是它自己那套云端路径
（`/115/…`），不是本机路径。在 Windows 上把这种字符串交给 `pathlib` 会得到一个看起来合理、
实际指向别处的结果。所以全程按字符串处理：归一分隔符、折叠重复斜杠、逐段拒绝 `.`、`..`、
盘符冒号与控制字符，再用用户配置的「前缀 → 已声明媒体根」表取最长匹配，拼出账本形态的
Windows 路径。前缀表里的根必须是已声明过的来源根，落不进表的路径整条丢掉，不猜。

**五、写完了才登记。** 事件到达先去抖 5 秒，然后读一次大小，等 4 秒再读一次，两次相等才算
写完；不相等就继续等，累计 1800 秒仍不稳定就放弃，留给全量扫描。临时后缀（`.part`、
`.!qb`、`.aria2` 等）和系统文件直接忽略。上游没有这一层判定，但 Peach 会在登记的同时读
时长、抽帧，对着一个正在写的文件做这些事拿到的是错的。

**六、事件风暴按队列削平。** 同一条路径的重复事件只把它的到期时间往后推，不排第二份；队列
上限 4096 条，满了丢新的并计数；登记串行，同一时刻只有一个文件在走入库。一次拷贝一百个
文件不会变成一百个并发的 `stat` 与抽帧。

**七、漏发由定期全量扫描补上，所以全量扫描不删。** watchdog 会在事件密集时丢事件，
CloudDrive2 会在 Peach 没起来的那段时间推空，前缀表配错会整类丢掉。这些都不当故障处理，
扫描照常跑，它仍是「账本与盘一致」的那个保证。推送只负责把延迟从一轮扫描缩到几秒。

**八、webhook 的三道门：来源、密钥、开关。** 只接受回环与私网地址来的请求；共享密钥独立
生成、存在 `<数据根>/secrets/push-discovery.json`（`0o600`），走 `X-Peach-Secret` 请求头而
不是查询串，比对用 `hmac.compare_digest`；通道没开就当端点不存在。三道门任意一道不成立一律
回 404，不回 401/403，因为对着扫描器承认「这里有个端点，只是你密钥不对」没有好处。这把密钥和
访问口令是两件事，轮换一份不影响另一份。

**九、默认关，开关在设置页。** 默认走纯扫描，用户在「媒体」分组里打开、配前缀表、抄密钥。
关掉就回到本 ADR 之前的行为，没有残留状态。只读端（reader）不起任何通道：它那份账本是复制
来的。`/healthz` 不加字段，运行状态放在设置页里。

## 被否决的方案

- **给 `A:` 和 `B:` 也挂 watchdog。** 递归 watcher 在网络挂载上就是轮询，正好是要避开的那笔
  流量。
- **推送成功就不再全量扫描。** 事件丢失是常态而不是异常，去掉补漏扫描等于把「账本与盘一致」这个
  保证换成「但愿没漏」。
- **用现有访问口令给 webhook 鉴权。** 那份口令是给人用的，会被用户改、也会出现在浏览器里；
  写进 CloudDrive2 配置文件的东西应该能单独轮换。
- **把密钥放在查询串里。** URL 会进日志和代理记录，AGENTS.md 里关于凭据的那条同样适用。
- **在 webhook 里同步做入库。** 那会让 CloudDrive2 的请求等到抽帧结束，超时重试再放大一遍。
  端点只做「收下、校验、入队」，204 立刻返回。
- **监听删除事件顺手把账本行去掉。** 网盘的删除事件和临时文件的删除分不开，误删账本行比晚
  发现一个空位贵得多。

## 后果

- 新依赖 `watchdog==6.0.0`，进依赖清单与 Dependabot。
- 多一个 POST 端点、一份设置（`push-discovery.json`）、一份密钥文件。
- CloudDrive2 那一侧要用户自己配一次 `webhook.toml`，步骤写在 [docs/CLOUDDRIVE.md](../CLOUDDRIVE.md)；这需要
  CloudDrive2 的会员功能。配不了也不影响本地通道和全量扫描。
- README 的运行方式多一句：新文件默认等扫描，打开推送发现后是秒级。

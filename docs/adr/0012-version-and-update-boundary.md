# ADR-0012：版本唯一来源与只检查更新边界

- 状态：Accepted
- 日期：2026-08-15

## 背景

Peach 曾同时在 `pyproject.toml`、`peach.__version__` 和 FastAPI 构造参数中保存版本，实际值
分别为 0.2.0、0.1.0 和 0.2.0。托盘「检查更新」直接在 Win32 消息线程运行 Git，再弹模态
MessageBox；仓库因 R: 盘所有权检查失败时只显示「无法读取」，确认框还会阻塞托盘交互。

主仓库现在有一个私有 GitHub remote（`origin`），并配了 Dependabot 与 GitHub Actions 测试
工作流。但 Codex/Claude 仍使用独立工作树，自动 pull 或覆盖工作树会破坏并行集成边界，所以
「检查更新」保持只读这条边界不变。

## 决策

- `src/peach/__init__.py::__version__` 是唯一版本来源；setuptools 通过 dynamic attr 生成包
  元数据，FastAPI health/OpenAPI 和托盘均读取同一值。
- 采用 pre-1.0 SemVer。修复升 patch；兼容功能升 minor；破坏性数据或接口变化升 minor，且
  必须同时有 ADR、正式迁移和验收。发布提交使用本地 `vX.Y.Z` tag。
- 托盘显示包版本、分支、八位提交、工作树状态和更新通道。所有 Git 读取显式传仓库级
  `safe.directory`，不修改用户的全局 Git 配置。
- 没有 `origin` 时报告「本地开发版、未配置更新源」。配置后，用户显式点击才在后台执行
  `git fetch --prune origin`，然后比较当前分支与 upstream 的 ahead/behind。
- 更新检查绝不 checkout、merge、pull、reset 或安装；发现更新只报告，在主检出按 worktree
  流程人工审核后集成。
- 托盘正常动作只使用 pystray 非模态系统通知。Git、网络和比较工作不得运行在托盘消息线程。

## 已拒绝方案

- **继续手工同步三处版本字符串**：已经实际漂移，无法作为发布依据。
- **点击即 `git pull`**：会覆盖或冲突于用户和 agent 的在途修改。
- **自建更新服务器/安装器**：当前没有可发布制品和远程通道，属于虚假复杂度。
- **模态 MessageBox 报告普通状态**：会阻塞通知区消息循环，HiDPI 下还暴露缩放问题。

## 后果

0.2.1 起版本、API 和托盘一致；更新检查可真实区分未配置、最新、落后、领先和分叉，但保持
只读。将来有签名制品后，可在新 ADR 中增加下载/验签/原子切换，不能直接扩展
当前按钮为自动覆盖工作树。

## 修订：档位由集成脚本判定（2026-09-05）

上面的 SemVer 规则从 0.7.x 起没有被执行：`scripts/agent_worktree.py integrate` 只会自动推
patch，功能与修复被记成同一档，一天之内从 0.7.24 走到 0.7.27。判定改为由脚本按提交类型做，
人不再逐次选档：

| 档位 | 何时动 | 判据 |
| --- | --- | --- |
| patch | 行为不变的修复、重构、文案、构建 | 合入的提交里没有 `feat`，也没有破坏性标记 |
| minor | 新功能，或数据格式有变 | 任一提交主题以 `feat` 开头或带 `!`，或 `migrations/` 新增文件 |
| major | 1.0：独立发行版可被陌生人开箱使用，配置与账本格式承诺兼容 | 手工 `--bump major`，并另立 ADR |

两档都以「改动进了运行时产物」为前提：只碰文档、技能与测试的集成不动版本号。
破坏性变化在 pre-1.0 阶段仍只推 minor，与上面的决策一致；`--bump` 显式档位是覆盖，`none` 表示不动。

## 修订：版本号跟发布走（2026-09-07）

上一节把档位交给脚本判，推进时机却还留在集成上：`integrate` 每次碰到运行时输入就推一格。
一天几十次集成于是各占掉一个版本号：2026-09-05 到 09-07 三天里 85 个 `chore(release)`
提交、其中 22 次 minor，同期只有 4 个 GitHub 预发布。SemVer 里「版本」的对象是发布物，
另外 81 个版本号没有任何制品对应，minor 位记的是「今天写了几个功能」。

- 版本号只在发布点推进，入口是 `scripts/release_tag.py --bump {auto,patch,minor,major}`。
  档位判据不变（`scripts/version_bump.py` 的 `bump_part_for()`），输入是「上一个版本标签到
  HEAD」这段区间；区间只碰了文档、技能与测试时拒绝发布，那样的包与上一个标签逐字节相同。
- `integrate` 不碰 `__version__`，结果里的 `version` 只是当前值。主线上跑的是哪一份由
  commit 认定：`build-info.json` 随包走，托盘按它算自己落后多少个提交。
- `/healthz` 报 `build_commit`（源码运行时是 null），`deploy_windows_tray.py` 按它核对生产
  入口。同一个版本号下会有很多个构建，只比版本号证明不了二进制换掉了。
- 发布必须带变更日志。`CHANGELOG.md` 按 Keep a Changelog 1.1.0 维护，`--bump --apply` 把
  未发布节定版成新版本号并写回文件、不提交；`--apply` 打标签前要求这一节存在。
- Release 页的正文就是那一节加一段安装提示，由工作流在标签提交上用 `changelog.py --notes`
  生成；缺那一节就不发，不拿固定文案顶替。使用者只读 Release 页，日志写在仓库里而
  没送到那里，等于没写。
- 整条发布链上只留一个需要人判断的点：那一节的措辞对不对。`--bump --apply` 把它原样带在
  输出里，确认之后 `--ship --apply` 一次做完提交、推送、等 Test 转绿、打标签。判据仍由脚本
  挡（不在 master、缺那一节、标签被占、工作区夹带别的改动都拒绝，Test 没绿绝不打标签），
  人不需要记流程走到了第几步。把「照着四步走」交给人是把机器该做的事外包出去：步骤本身
  没有判断，判断只在措辞上。
- 预发布后缀（`0.29.1-beta`、`0.0.1a` 这类）不采用。0.x 本身就是 SemVer 第 4 条声明的初始
  开发阶段；后缀在规范里表示「同一目标版本的候选序列」，需要一个目标版本才有意义，唯一
  该用它的时机是 1.0 之前那一轮 `1.0.0-rc.N`。PEP 440 还会把 `0.29.1-beta.1` 归一化成
  `0.29.1b1`，让包元数据与 tag 不相等，正是本 ADR 第一节要消灭的那种漂移。「还在测试阶段」
  由 GitHub 预发布标记、README 的 pre-1.0 与托盘的更新通道表达，不写进版本号。
- 已发的 tag 与已占用的版本号一律不动：SemVer 第 2 条要求版本号只增，第 3 条要求已发布的
  内容不可再改。`0.28`–`0.29` 这些没有制品的号码就此空掉，下一次发布从当前 `__version__`
  往上推。`CHANGELOG.md` 补记的是已有制品的那几个版本，不重编号、不改 tag、不换制品；
  已发布 Release 的正文可以补成 `CHANGELOG.md` 对应那一节，说明文字不是发布物的一部分。

## 1.0 门槛（2026-09-07）

1.0 缺的不是功能清单，是**承诺面**：1.0 之后每一次破坏性变化都必须推 major，没有明确的
承诺面，major 位只是装饰。下面八条全部成立才发 `1.0.0`，之前那一轮候选写成 `1.0.0-rc.N`。

| # | 条目 | 现状（2026-09-07） |
| --- | --- | --- |
| 1 | Windows 与 macOS 都有独立制品，运行不依赖本机源码安装 | Windows 有，macOS 仍是源码运行 |
| 2 | 独立包能自行更新，失败可回滚 | Windows 已在页面内下载安装并回滚，macOS 缺制品 |
| 3 | 全新机器（无 `peach-data`）上从制品完成一次真实开箱验收 | ADR-0023 在源码形态实测过，制品形态需重跑 |
| 4 | 账本 schema 承诺：1.0 后需要导出重建才能升的迁移算破坏性变化，推 major | 未声明 |
| 5 | `config.toml` 键名冻结，改名必须带迁移器并保留一版兼容读取 | 未声明 |
| 6 | HTTP API 分公私：点明哪些路径是对外契约，其余随时可改形状 | 未声明 |
| 7 | 双语 README 对齐，另有 SFW 演示数据集 | README 已对齐，数据集在待办 |
| 8 | 待办第 14 条「制品与更新渠道」关闭 | 未关闭 |

第 4、5、6 条是纯声明，不需要写代码，但一旦声明就不能反悔，所以要与第 1、2、3 条同批确认。

「退出测试阶段」在本仓库有确定动作，三处一起改：`release.yml` 去掉 `--prerelease`、README
去掉 pre-1.0、托盘的更新通道文案改成正式通道。它可以先于 1.0 发生（例如某个 0.x 起发正式
版），也可以与 1.0 同时；但不要把它和「功能齐了」绑在一起，决定它的是承诺面，不是功能数。

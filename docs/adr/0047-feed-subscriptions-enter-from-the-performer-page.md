# ADR-0047：订阅只从人物页进，订阅源只有 JavDB 演员页一类

- 状态：Accepted
- 日期：2026-09-23
- 关系：收窄 [ADR-0042](0042-feeds-discover-codes-not-files.md)「后果」里「能用的只有
  sukebei 的原生 RSS 与 JavDB 演员页伪 Feed 两类」，其余各条不变

## 背景

ADR-0042 落地时有两个入口：设置页「订阅源」下面一张表单（来源类型、拉取间隔、订阅地址、名称），
和人物页资料卡上的「订阅新作」开关。开关按这位的 JavDB 身份现拼演员页地址，页面只送开和关。

用了一天之后的情况是：库里的订阅全部来自人物页的开关，表单一条都没建过。表单唯一多出来的用途
是手填 sukebei 的 RSS 地址，而那种源不绑定任何人。它发现的新作只能出现在首页，
人物页那一块看不到。用户看到表单时问的是「这里填写后会发生什么，在哪里更新」，
说明它在界面上没有自己的位置。

## 决策

**一、订阅只从人物页的「订阅新作」开关进。** 设置页「订阅源」只列已有的源，
能开关、移除、立即拉取，不再收地址。`/api/feeds/source` 只认 `follow`、`enabled`、`remove`
三个动作，页面送来的地址一律不收。

**二、订阅源只有 JavDB 演员页一类。** RSS/Atom 的解析、`rss` 类型、拉取间隔的上下限与
设置页的类型下拉一并清退。`feed_source.kind` 列保留：它是解析器的分派键，拉取时认不出的类型
按解析失败写进那一行的 `last_error`，不拿演员页的解析器硬读。

**三、拉取间隔固定为默认的 6 小时。** 间隔原本只有表单能改，而 JavDB 按出口 IP 计配额，
一张一天更新几条的演员页没有拉得更密的理由。

## 被否决的方案

**只留地址一栏，类型按地址判断。** 入口少了两个字段，问题还在：手填的源不绑定人物，
发现的新作在人物页上看不见。要让它有位置，就得再做「这条源属于谁」的选择，
那又是一个人物页开关已经回答了的问题。

**保留表单不动。** 四个字段里有三个在唯一的实际用法里用不上，而「任意 HTTPS 地址」
是这个应用里又一处由页面决定去哪发请求的入口。

## 后果

- 设置页「订阅源」只剩列表、开关、移除和「立即拉取」。
- 想盯 sukebei 这类不按人组织的源，需要重新设计「这条源的新作挂在哪」，再新增 ADR。
  源的取证记录留在 [docs/SOURCING.md](../SOURCING.md)「番号发现源（Feed）」。
- 账本里若有 `rss` 类型的旧行，它会在下一轮拉取时报解析失败，在设置页那一行下面看得到，
  可以直接移除。

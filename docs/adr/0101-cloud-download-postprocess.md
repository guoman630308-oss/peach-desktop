# ADR-0101：云下载入库后自动处理本次落地范围

- 状态：Accepted
- 日期：2026-10-10
- 相关：ADR-0039、ADR-0040、ADR-0089

## 背景

云下载原来在 `scan.ingest_path` 登记文件后就结束。一个种子有正片、短推广视频和网址附件时，
任务会把最早登记的资产当成正片；任务带来的番号没有写回资产，资料处理与整理也不会启动。
结果是任务显示「已入库」，馆藏里却仍是无番号、未刮削、未整理的云下载目录。

用户明确要求云下载形成闭环，并接受本次下载的文件自动进入既有整理模板。这项授权只覆盖
云下载刚落地的范围，不改变扫描既有媒体时的默认边界。

## 决策

**一、传输完成与后处理分别记状态。** `download_task.state='ingested'` 仍表示远端文件已登记；
`postprocess_state` 单独记录待处理、排队、进行中、完成与失败。升级前已经入库的任务补为待处理，
服务启动时补派。

**二、先识别正片。** 在本次落地目录的活动视频中，依次按番号一致、非推广命名、时长、分辨率、
体积选择主资产。文件数不是拒绝条件；缩略图、NFO、字幕和少量推广附件可以共存。

**三、复用既有写入链。** 任务提交时携带的番号只在主资产字段为空时按 `scan:filename` 归属写入；
资料采集调用 `process_library(..., retry_ids=[主资产], stage='collect')`；推广附件复用垃圾复核分数，
只有达到既有自动线的附属资产才进入 ledger 回收站，不永久删除文件。

**四、整理只作用于主资产。** 后处理读取该来源已经保存的整理模板，生成只含主资产的计划；执行前
备份 SQLite，沿用整理批次日志、撞名拒绝、同卷移动与云盘核验门槛。没有模板或来源缺核验通道时
跳过整理并在任务摘要说明，不扩大为全库整理。

**五、后处理是持久后继。** 下载对账只声明 `download-postprocess:<task_id>`，由 ADR-0040 的 ledger
串行通道执行。进程重启时未完成后继重排；每一步可重复执行，成功状态是唯一的完成判据。

这是 ADR-0039「没有自动整理」的窄例外：只针对用户主动提交的云下载、只处理本次主资产，既有媒体
扫描、全库资料处理与手动整理的默认行为不变。

## 后果

- 云下载列表可以区分「已入库」和「后处理完成」，失败原因留在任务上。
- 自动隔离只改 ledger 的 `disposal='trash'`，清空回收站仍是独立、显式的永久删除操作。
- 磁力元数据不能证明画面是否有嵌入水印；非 manko.fun 候选保留待检查状态，不能把“未知”写成“无水印”。

# ADR-0040：任务在结束时声明后继，调度端统一派发

- 状态：Accepted
- 日期：2026-09-22

## 背景

刮削链每跑一轮都会往账本里登记新的 performer 与 studio 实体。这些实体刚建出来时没有头像：
人物页那张圆图退成作品抽帧，厂牌页退成首字母。补头像的能力早就有：`avatar_picker` 的
图库候选、`scripts/fill_portrait_gaps.py` 的「图库只命中一张就装」、`harvest_social_avatars.py`
的社媒头像、`fetch_studio_avatar_candidates.py` 的厂牌 Logo，但它们全是人想起来时手工跑的
脚本。结果是刮削发现的新实体和补头像之间隔着一次人工，隔多久取决于有没有人记得。

把补头像塞进 `process_library` 里面是最省事的做法，`_enrich_finished_performers` 就是这么来的：
它跟在采集之后、同一个函数体里、同一条进度上，只处理 r18 profile 直接给出头像地址的那一种。
再往里加就要在一个已经 250 行的 `try` 块里接第三、第四个外部来源，而它们的失败、限流和
重试判据彼此不同，那不是一个函数该承担的形状。

参考实现 amane 把这件事拆成「任务结果声明后继、调度端统一派发」（证据与判据见
[docs/reference-snapshots/amane-task-followups.md](../reference-snapshots/amane-task-followups.md)）。这个形状正好答上面那个问题：补头像是
一件与刮削无关的事，它只是恰好由刮削触发。

## 决策

**一、后继由任务结果声明，不由任务中途派生。** 一轮任务只能在自己结束的那一刻，把
「接下来该做什么」作为结果的一部分交出去；执行中不许起线程、不许直接往队列里写。中途
派生的后继无法回答两个问题：任务被停止时那些已经飞出去的线程归谁管，以及一轮任务的
影响面到底有多大。声明式的后继两个都能答：影响面就是结果里那张表。

**二、同 key 去重，去重在插入那一刻由数据库判。** 后继的 key 是它要做的那件事的全名
（`entity-avatar:performer:8022`），不是任务类型。同一个 key 已经有一条在排队或在跑时，
新的那条不入队。判据用 `task_run` 上现成的活跃互斥唯一索引，撞上 `IntegrityError` 才算冲突，
不先查一遍，因为先查再插之间那个时间窗正是重复入队的来源，这条判据与 `task_runs` 的第 2 条
不变量是同一条。

**三、写账本的后继串行，其余按类型并行。** 后继类型在注册表里声明自己写不写账本。写的
那些共用一条串行通道，一次只跑一条；不写的各按类型一条通道。Peach 的账本是单文件 SQLite，
并发写只会撞在写锁上，串行不是保守而是如实反映真实约束。

**四、后继失败不回滚父任务，也不改父任务的结论。** 补头像没取到不代表刮削没成功。后继
自己在任务中心留一条失败记录，父任务那条保持原样。反过来也成立：父任务失败时一条后继都
不派，`result.success` 是派发的前置条件。

**五、数量与深度都有硬上限。** 单轮任务最多派 `MAX_FOLLOWUPS`（64）条后继，链深度最多
`MAX_DEPTH`（2）层。超出的不静默丢弃：入队时截断，截断了多少条写进父任务的结果摘要，
活动页看得见。没有这道闸时，一条「后继再派后继」的规则加上一次全库刮削就是几万条任务，
而它在代码评审里看不出来：上游 amane 就没有这道闸（那份证据里记作「未取得」）。

**六、未跑完的后继在重启后重新排队，代价是后继必须幂等。** `pending` 的后继本来就是库里
的行，重启后照常被领走。停在 `running` 的后继改回 `pending` 重跑，而不是像普通任务那样
判成 `interrupted`，因为 `peach-batch-jobs` 的续跑判据是「只把成功判定当作已完成」，把一条没
跑完的后继冻死在终态就再也没有重试机会。因此每个后继处理器都必须可重复执行：补头像先看
盘上有没有那张图，有就当场返回。重跑上限由后继自己的 key 去重与幂等保证，不另设重试计数。

**七、第一批后继只有补头像一种，只走已有判据。** 作品刮削成功、这一轮新登记了 performer
或 studio 实体、该实体盘上没有头像，三条同时成立才派一条 `entity-avatar` 后继。它走
`avatar_picker` 现成的三步（`choices` / `resolve` / `install`），落图规则原样沿用
`fill_portrait_gaps.py` 的那一条：图库里按这个人整条名字链只找出一张、且尺寸过
`acceptable_avatar` 那一档，才装；找出好几张一张都不装，记成待人认。厂牌没有对应的免复核
判据（`fetch_studio_avatar_candidates.py` 的 handle 要人给，猜出来的一律 `needs_confirmation`），
所以厂牌只登记缺口，不自动装图。后继不新增任何自动落图规则，越过现有判据要另写 ADR。

## 后果

- `task_run` 多出四列（`parent_run_id`、`root_run_id`、`followup_key`、`followup_depth`），
  父子关系落在同一张表上，不另开边表，因为 Peach 是单进程单文件 SQLite，一张表查得完。
- 活动页与 `/api/tasks/{run_id}` 能看见父子关系与后继状态；后继是独立的一轮，有自己的
  开始时间、错误和摘要。
- 刮削之后新登记的女优不再靠人手跑 `fill_portrait_gaps.py` 才有头像；图库认不准的那些仍然
  留给人，判据一个字没变。
- 后继处理器必须幂等，这条约束写进注册表的文档而不是靠记性。
- 原先内联在 `process_library` 里的 `_enrich_finished_performers` 保持不动：它处理的是 r18
  profile 顺带给出的官方头像地址，与图库那条路不是同一件事，两者叠加的结果是「官方有就用
  官方的，没有再看图库」。

## 未决

后继的优先级、取消一整条链、手动重跑某一条后继都还没有。第一批只有一种后继类型，这些在
它身上都没有对应的用户动作；等第二种类型进来再定。

# ADR-0042：Feed 只发现番号，未入库的新作不进 asset 表

- 状态：Accepted
- 日期：2026-09-22

## 背景

「关注的女优出新片了」这件事，Peach 现在只能靠人自己去外面看。刮削链是被动的：先有文件，
才有番号，才有资料。关注（`follow_*`）那一套盯的是创作者的图文与视频帖，不认番号。
结果是同一个人在两个地方各被关注一次，而番号那一侧根本没有「新作」这个概念。

参考实现 amane 把这件事做成了 Feed：订阅若干 RSS/Atom，按源的间隔拉取，只从条目里解出番号，
产出一条 by-number 的刮削任务，**不下载 enclosure、不写入媒体库**（设计判据见
[docs/reference-snapshots/amane-feed.md](../reference-snapshots/amane-feed.md)）。这个形状正合适：Peach 要的也只是番号。

来源这一侧先做了取证（[docs/SOURCING.md](../SOURCING.md)「番号发现源（Feed）」）。结论是原生 RSS 在这个领域
基本绝迹：FANZA、MGStage、一本道、カリビアンコム、Tokyo-Hot、AVBase、javtrailers 全部没有，
javlibrary 与 RSSHub 公共实例挡在 Cloudflare 后面，JavBus 有人机验证。**能用的只有两类**：
sukebei.nyaa.si 的原生 RSS（75 条里 50 条带番号），和 JavDB 演员页当伪 Feed 抓（40 条里 39 条）。
DUGA 那份看起来最正规的 RSS 反而不能用：它的条目只带站内商品号，解出来是
`PARADISETV-5258` 这种任何来源上都不存在的假番号。

所以这件事的难点不在 RSS 解析，在「新发现的番号该以什么身份存在于 Peach 里」。

## 决策

**一、Feed 只发现番号。** 一次拉取的全部产物是：一条「这个源见过这个条目」的记录，
和一条「这个番号还没入库」的记录。不下载种子、不下载 enclosure、不建目录、不碰任何媒体文件。
条目正文、附件、封面图一律不存：Feed 不是阅读器，正文留着只会让人想去渲染它。

**二、未入库的新作不进 `asset` 表，单独一张 `feed_discovery`。** `asset` 的语义是「盘上有这个
文件」，整个系统都按这条读它：`scan` 用 `last_seen` 落后表达文件消失、`web_resource_sync`
现场 `stat` 并清掉真的不在了的行、`organize` 按 `asset.path` 搬文件、抽帧按路径开 FFmpeg、
馆藏统计数的是 `asset` 的行数。往里塞一行没有文件的记录，等于要在这五处各加一个例外，
而且每处例外的判据都不一样。**不加状态列**（`missing` / `offline` / `placeholder` 都不加）：
加了之后「这一行算不算馆藏」就变成每个调用方各自解释的问题，而现在它不用解释。

代价是查询要跨两张表，收益是边界由表结构保证而不是由纪律保证：`feed_discovery` 不进整理、
不进抽帧、不进馆藏统计，因为它根本不在那些代码看的那张表里。它也**不登记进
`web_batch.ASSET_REFERENCE_TABLES`**：那张表是「物理删除资产时要清的引用」，而发现记录不引用资产。

**三、番号入库与否是现算的，不落列。** 一条发现记录算不算「已入库」，看的是
`asset` 里有没有同番号的行，查询时 JOIN 出来。不在 `feed_discovery` 上存一个 `in_library` 布尔：
存了就要在扫描、导入、删除、回收站还原五个地方同步它，而这五个地方谁都没有义务知道 Feed 存在。
真相只有一份，投影现算。

**四、去重两层，各管各的。**

- **源内**：`UNIQUE(source_id, item_key)`，`item_key` 按 `guid` → `link` → `title` 回退。
  解不出番号的条目照样记一行（`code` 为空），否则每轮都会对同一个垃圾标题重试一遍。
  这一层只回答「这个源的这一条我见过没有」。
- **全局**：`feed_discovery.code` 全表唯一，且建之前先查 `asset`，已入库的番号不建壳。
  这一层回答「这个番号需不需要一个壳」。两个源同时报同一个番号，只会有一个壳，
  但两条 `feed_item` 都留着，因为它们各自是各自源的去重真值。

整份文档那一层（`ETag` / `Last-Modified` → 304）也做，但**不能当作可以依赖的东西**：
sukebei 两个响应头一个都不给（2026-09-22 实测）。304 只是省一次解析，不是去重判据。

**五、已读与忽略是两列，彼此正交，都不改变去重。** `read_at` 表示用户看过，`ignored_at`
表示用户不想再看见。忽略保留记录与去重关系：后续拉取不会重新建壳，这正是忽略的意义。
取消忽略只恢复可见性，不自动派刮削。两列都不参与任何唯一约束。

**六、刮削走现有来源链，由后继机制派。** 一轮拉取按 ADR-0040 声明一条后继
（`feed-scrape:<番号>,<番号>,…`），带上这一轮新建的壳，余下名额给还缺资料或本机封面、
距上次尝试已过 12 小时的旧壳（手动点「检查」的那一轮不等这 12 小时）；活动页上一轮订阅
因此是一行，不是一部一行。后继内部用
`metadata_routes.route_for_code` 算链、用 `library_processing.LibraryMetadataProvider` 发请求，
取到的标题、女优、厂牌、发行日与封面地址写回壳自己的列。**不复用 `process_library`**：
那条路以 `asset` 行为单位、要写候选 CSV、要按字段优先级链结算，而壳没有真相字段可写：
壳上的每个值都只是「某个来源这么说」，用户复核的时机是文件真的到手、建成 `asset` 之后。

封面走馆藏那一条：`jav_cover_fetch.best_cover` 从官方渠道取图，`cover_artwork.install_cover`
连同书脊正封框与人脸边车装进本机封面目录，新作卡与资产卡按同一份边车取景，入库后原样就是
它的封面。第一条不存的是 Feed 条目自带的图，与这里无关。

后继的幂等性由 ADR-0040 要求：重跑一次只是把同样的值再写一遍，本机已有的封面不再取。

**七、番号解析先切词元。** `catalog_rules.release_code_from_text` 是按整段文本判的，
对 `HMN-071 新人 帶來超稀有妹子…[有碼高清中文字幕]` 这种标题只认出 75 条里的 3 条；
先按空白与括号切成词元再逐个试，认出 50 条。Feed 侧因此有一个 `scan_code`，
它只是 `release_code_from_text` 的外圈，**不另写一套番号正则**，因为两份实现漂移会产生
两个封面缓存键，这是 `catalog_rules` 自己注释里记着的旧伤。

**八、拉取限流按既有的来源预算，不因为是后台任务就另开一套。** HTTP 一律走
`peach.http` 的 transport，主机间隔沿用 `library_processing.SOURCE_INTERVALS`
（javdb 3 秒），403 整源停下、冷却判据在 `scraping_access`。定时机制复用
`follow_scheduler` 那一个 APScheduler 实现（参数化出 job id 与状态文件名），
不再起第二套间隔、退避与状态上报。

## 被否决的方案

**在 `asset` 上加 `missing` 状态列。** 最省事，也最贵：五处按「行存在等于文件存在」写的代码
要各加一个例外，而它们分属扫描、同步、整理、媒体与统计五个域。更糟的是这个列会长出第二种
用法（真实文件临时离线的那种），于是同一个值表达两件事。

**把壳做成 `asset` 的一行，路径写成占位串。** `UNIQUE(location, path)` 上的占位串会被资源同步
当成「盘上没有」而清掉，清掉之后下一轮 Feed 再建一遍，形成一个谁都没察觉的循环。

**做成完整的 RSS 阅读器**（正文渲染、分组伪路径、OPML 导入、键盘导航）。上游有这一套，
Peach 不要：这里的目标是「看见新作」，不是「读订阅」。正文一旦存下来就会有人想渲染它，
而正文里带的是站外图片和跟踪链接。

**复用 `process_library` 给壳刮削。** 它以 `asset` 行为单位，要写候选 CSV、要按字段优先级链
结算到真相字段。壳上没有真相字段，复用它就得先给壳一行 `asset`，绕回上面那个被否决的方案。

## 后果

- 新增三张表与一条迁移：`feed_source`（订阅）、`feed_item`（源内已见条目）、
  `feed_discovery`（未入库的番号壳）。壳与实体的关联单独一张 `feed_discovery_entity`。
- 「未入库」在界面上是一类**明确标注**的东西，不是看起来像资产的东西。首页与人物页的
  「新作 · 未入库」区块用与目录卡同一套形状，但点开去的是外站作品页，不是播放器。
- 馆藏统计、整理、抽帧、资源同步、回收站的口径全部不变，因为它们看的表没变。
- 用户能订阅的来源受现实限制：能用的只有 sukebei 的原生 RSS 与 JavDB 演员页伪 Feed 两类。
  这个清单会随站点变化，判据（「条目里那串东西是不是真的番号」）写在 [docs/SOURCING.md](../SOURCING.md)。
- 一个源接进来之前必须先看它的番号样本。DUGA 那种「RSS 很正规、番号是假的」的来源
  只有人看一眼才能判出来，没有自动判据。

## 未决

**壳什么时候该消失。** 现在的判据是「同番号的 `asset` 出现了就不再显示」，但壳本身不删，因为
删了就失去「这个番号已经发现过」的记忆，下一轮会重建。留着的代价是这张表只增不减。
按量定期清退（比如已入库且已读超过一年的）需要先知道真实增长速率，本次不定。

**同一番号的多源证据。** 两个源报同一个番号时，第二个源的条目记下了，但壳只记第一个源。
如果以后要拿「几个源都报了」当置信度，需要在壳与条目之间建多对多关系。本次不做：
现在能用的源只有两类，其中一类是按人绑定的，重叠面很小。

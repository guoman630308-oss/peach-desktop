# ADR-0034：只有一家社区来源也补空，社区来源不一时取 javdb

- 状态：Accepted
- 日期：2026-09-16

## 背景

官方来源存在页面时也可能缺少出演者或系列；若只因社区来源数量不足而拒绝补空，可靠字段会停留在人工队列。

用户 2026-09-16 的两次决定：

- 「如果只有一个总比没有好，只有javdb等单方的也采用」；
- 「我检查了下javdb数据比javbus更准确，优先采用它的」。

## 决策

**一、只剩一家社区来源时照样补空。** `_evidence_candidates` 不再因为来源只有一家社区站而
返回空。落库仍只补空格子（ADR-0033），其余门槛（文件名认得出番号、MIB 只认官网、用户判过
的字段不碰、出演者剪得出艺名）不变。

**二、社区来源取值不一时取 javdb。** 在场的全是社区来源、javdb 自己只给一个值时，落 javdb
那一侧，`review_decision.note` 的规则名记 `adr-0034-empty-field-javdb-preferred`。有官方来源
或本地 NFO 在场的分歧照旧交给人。

**三、日期式番号的发行日期只认番号那天。** `MMDDYY-NNN`／`MMDDYY_NNN` 的片商按发行日编号，
候选里等于番号日期的才算；有人给了这一天就落它（规则名 `adr-0034-empty-field-code-date`），
谁都没给就交给人。

## 理由

- 补空不覆盖任何值。空着的格子上错一个值，代价是用户改一次，改过就归 `user:manual`，
  自动写入再也不碰；一直空着的代价是整行卡在队列里等人。
- javdb 优先是用户逐条核对后的结论，本机队列里的例子也站得住：`MAAN-545` 的厂牌 AVBase
  给 `DOC`，javdb 给 `プレステージプレミアム`。
- 番号日期是片商自己的编号规则，比任何转录站都硬。队列里 `092415_001` 的发行日期 javdb
  给 2016-06-16、javbus 给 2015-09-24，番号写的是后者；javdb 那个是转售商的上架日，第二条
  不加这一道就会把它落进账本。

## 被否决的方案

- **保留两家一致的门槛。** ADR-0030 担心的 `ABW-358` 上架日问题真实存在，但它让大批只有
  javdb 收录的片永远卡在人工，这里选择先有值。
- **按字段来源顺序取排名最高的一家。** 顺序表管的是官方来源之间的先后，AVBase 根本不在表里；
  把「社区之间听 javdb」写进顺序表会连带改动官方来源的署名逻辑。
- **官方与 javdb 分歧时也取 javdb。** 用户比较的是 javdb 与 javbus，没有说 javdb 比官方准。

## 后果

- 只有 javdb 一家收录的片，空字段直接补上；错值只能靠用户发现后手改。
- `ABW-358` 这类「javdb 给的是 MGS 上架日」的错值会落库，发行日期字段的正确率低于两家印证时。
- 回溯社区来源写入的值：`review_decision.note` 的 `rule` 分得出单家补空（`adr-0018-...-single-community-source`）、
  javdb 取舍（`adr-0034-empty-field-javdb-preferred`）与番号日期（`adr-0034-empty-field-code-date`）。
